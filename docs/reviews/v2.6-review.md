Reviewed 2026-11-05. **Recommendation: do not merge or deploy this branch as-is.** Preserve the useful pilot-workflow ideas and selectively remake them on current master after the decisions and checks below. ## Blocking findings for integration

### P1 — The branch's formula, bundle and response versions disagree with master

The branch [declares output `attached-marker-ellipse-14451-v2` while requiring a 11900 bundle][b-method], and its [loader rejects manifests unless method and divisor are 11900][b-load]. The [current approved manifest][m-manifest] says 14451-v1 and 14451. A synthetic in-memory run of the branch loader with that actual manifest returned `model_bundle_invalid`; no inference or private photo was used. In addition, the [branch web response guard expects 14451-v2][b-guard], while [master expects 14451-v1][m-guard], so independently deploying one side can reject otherwise valid responses. A mechanical integration can therefore leave inference unavailable or produce an incompatible response.

The [accepted ADR][m-adr] requires the method, divisor and content-derived bundle ID to agree and excludes old 11900 bundles. Compared with master, the branch also lacks master's [`bundle_identifier` validation][m-bundle]. Keep master's formula, versioned manifest, hash/identity checks, approved three serving artifacts, and Decimal price snapshot behavior. If a new method contract is ever required, version it deliberately and update the exporter, manifest, backend, frontend, examples and compatibility tests together; do not relabel an old manifest or modify trained artifacts just to make this branch load.

### P2 — Manual camera capture discards a new photo on transient errors

In the branch, [manual capture waits for server validation before `onCapture`][b-manual-camera]. A 429, 503 or network failure leaves the new camera image inside the failed attempt rather than selecting it for retry or download. Even a 422 prevents review of the new still. Successful camera captures are checked again when [the selected photo enters the normal queue][b-photo-queue], duplicating work. This conflicts with the current product's retryable selection flow, in which a selected file remains available on busy/unavailable/connection failures.

On a remake, hand the still to the existing selected-file queue and preserve its status and explicit Retry; treat rejection separately from transient failure. If automatic capture needs candidate checks, keep the user's manual capture and its review/retry path available. Test 422, 429, 503, network interruption, cancellation and a successful capture with exactly the intended checks.

### P2 — Reopening an attempt silently drops its saved review state

The export [writes `estimate.json`, CSV, the original pair and inspection images][b-export]. The import [filters the ZIP to two photo names and ignores all other entries][b-import], then [selects those photos and restores only ID and attempt][b-import-ui]. Selecting photos clears review and corrections. Thus a reopened, previously corrected attempt returns to newly detected points rather than its saved edits; existing measurements, scale-weight field and price/provenance are not restored into the review. Re-exporting can make a new archive with the same apparent attempt label but different state. The original downloaded archive is not deleted.

Specify whether reopening means **restore an archived review** or **reanalyze the original photos as a new result**. If restoring, validate and bind versioned metadata and corrections to the exact images and keep the original record distinct from any recalculation; if reanalyzing, clearly label it and retain prior values separately. Cover missing or malformed metadata, ID/photo mismatch, duplicate names, size limits, EXIF orientation, version changes and export/reopen/re-export round trips. No claimed pig identity can be inferred solely from a filename.

### P2 — Manual coordinates can change an anonymous result without an explicit result-level provenance marker

The public estimate endpoint accepts correction JSON and [applies in-image coordinates to measured landmarks][b-correct]. It validates names, numeric types, image bounds, some pose ordering, projection and measurement arithmetic, but does not establish that a moved point is anatomically correct or even inside the detected pig box. A bounded synthetic test placed a corrected point within the image but outside a synthetic detection box; the branch accepted it. This is not an admin-authentication bypass: estimating is intentionally public. It is a trust and provenance boundary because corrections influence both weight and the ensuing Decimal valuation.

The branch includes original detections in diagnostic data for a corrected view, but [returns the normal estimated status and method][b-estimate-result]; consumers ignoring optional diagnostics cannot distinguish automatic from human-adjusted results. The overlay also calls all white dots pose landmarks. Before enabling this publicly, define who may correct, what additional geometric checks are justified, how an output and export identify detected versus manually supplied points, and how original points, adjustments, image identity and calculation version remain reviewable. Do not treat a human edit, the 20–30 kg message, or an engineering check as proof of anatomy, physical marker scale, same-pig identity or accuracy. Keep rejection on genuinely unusable image/marker/projection evidence rather than bypassing it to force an estimate.

### P2 — The editable length preview can disagree with the actual projected measurement

In review mode the [frontend redraws body length from the arithmetic midpoint of the two ear pixels][b-overlay-lines]. The [backend instead averages the projected ear positions and inverse-projects that midpoint][b-projected-lines], as required by the implemented geometry. Under perspective those points generally differ, so the cyan preview can mislead a user inspecting or adjusting the line. A synthetic homography check produced image-space midpoint `[50, 20]` and projected midpoint approximately `[39.333, 20]`; these are geometry-test coordinates, not animal measurements. Use the same transform/definition for the preview and final overlay, or clearly avoid presenting an approximate line as the measured segment. Test skewed marker geometry as well as the unskewed case.

### P2 — Point editing is pointer-only, and the standard flow becomes two-step

The branch provides [pointer handlers on SVG circles][b-pointer] but no keyboard-reachable control or coordinate/keyboard alternative for moving a point. Users who cannot drag can calculate with detected points but cannot perform the advertised review. Provide labeled, focusable, keyboard-operable controls with visible focus and a touch-friendly equivalent. The form also replaces the direct estimate action with mandatory [Review points, then Calculate weight][b-review-ui], adding another pair upload and inference pass. Whether this should be mandatory for every visitor, opt-in for pilot review, or otherwise scoped is a product decision; do not silently change the established flow when porting the useful editor.

The [SVG uses the decoded-image dimensions as its viewBox and maps pointer coordinates through the inverse screen transformation][b-pointer]. Source inspection does not establish a separate pointer-offset or letterboxing defect; the preview midpoint issue above is a different calculation. Browser checks should still cover resizing, SVG aspect fitting, portrait/landscape photos, EXIF orientation and pointer alignment before and after a drag.

### P3 — Malformed diagnostics can pass the guard and crash the editor

The [diagnostic guard][b-diagnostic-guard] checks the types of present entries but not the required names for each view or line. A synthetic invocation of the actual branch guard accepted a top diagnostic with an empty landmarks object and a `body_length` line. The editor then [destructures the missing ear points][b-overlay-lines], which raises `TypeError`. This requires a malformed or incompatible response; the normal branch backend supplies the points. Validate view-specific required fields and finite, plausible dimensions before rendering, and show a recoverable response error. Also validate the optional diagnostic structure in estimate responses rather than accepting any object.

## Capture, retention and operational boundaries

- **Auto capture is repeated upload, not just a local guide.** [The loop][b-auto] encodes and sends a still, retries 422 and 429, and waits 850 ms before the next iteration with no overall attempt/time limit. [The surrounding copy][b-upload-copy] only says a captured photo is sent. Explain the repeated still-image uploads before opt-in, provide an obvious Stop, cap/back off busy and repeated failures, and test multi-client contention with the single CPU inference slot. The server's cancellation handling deliberately lets CPU work finish before releasing resources, so aborting a browser request is not proof that server compute stopped.
- **Downloads persist locally.** The save buttons and ZIP are user-initiated, not evidence of new server-side image storage. However, original uploaded files may carry EXIF metadata, and ZIPs contain identifiable pilot labels, images, measurements and possibly price data. Product scope leaves image-retention, consent and deletion details open; explain local persistence and metadata and decide handling before adopting a pilot retention workflow. Do not place private photos, ZIPs, training data or credentials in Git.
- **New rejection gates are proposals, not proven improvements.** The branch adds boundary-box clipping and chest-order/cross-axis checks and a few synthetic preflight tests ([B source][b-pose-gates], [B tests][b-pose-tests]). They may reject legitimate captures, and a model box not touching the boundary cannot prove an entire pig is visible. Evaluate true/false rejection using appropriately consented real captures and keep the results separate from physical weight accuracy. The branch's 20–30 kg message is based on predicted weight; the ADR does not implement a scale-weight eligibility rule.
- **Manual review has a defined current limit, not zero value.** Both the [UI's photo-check prerequisite][b-review-ui] and the server's [pre-correction pose gates][b-correct] prevent editing low-confidence, out-of-image or already misaligned detected points. The editor does work on points that pass those gates but are misplaced. Decide whether a separate, safely designed rescue mode is intended; never simply bypass marker, image, projection or final measurement checks. The branch documentation itself describes review *after* checks pass.
- **Auth and prices:** the diff does not alter [authenticated price publication][b-auth-price], nor [the post-inference Decimal valuation and price snapshot][b-valuation]. Preserve and regression-test these boundaries, request-Origin enforcement, multipart limits, cancellation and unavailable/rejected outcomes when adding diagnostic or correction fields. The new `review`/`diagnostics` query and correction multipart field change a public route; [branch curl examples][b-example] are illustrative and were not exercised end to end in this review.
- **Torch and layout:** torch support is feature-detected and failures are displayed, but [the toggle][b-torch] is not proof of physical-device behavior. If track settings omit `torch`, the code accepts a resolved constraint call as success without independently confirming the light. Master's newer square guide, smaller dimensions and landscape layout must remain the starting point. Confirm track shutdown on close, hidden tab, denied permission, rejected constraints and delayed promises; test supported and unsupported devices after shared-resource confirmation.

## Suggested implementation sequence and gates

These are proposed future conventional commits, not authorization to implement or deploy:

1. `feat: add pilot photo export` — establish deliberate local save/retention and pair provenance; keep original photos and result metadata distinct. Add a versioned, bounded archive schema and round-trip tests.
2. `feat: add measurement diagnostics` — add response-validated overlays on master's 14451 pipeline, with perspective-correct geometry, optional UI and explicit bounds. Evaluate additional pose-rejection rules separately before enabling them.
3. `feat: support reviewed landmark adjustments` — settle who may adjust, review/identity/provenance semantics, accessibility and optional versus mandatory flow. Exercise valid and malformed corrections, unavailable models, hard rejection gates, edited/unmodified result labels, Decimal valuation and a real end-to-end example for each changed public-route mode.
4. `feat: reopen saved pilot attempts` — restore or explicitly reanalyze according to the chosen archive contract; test errors, mismatches and changed method/model versions. Never silently imply an old result was recalculated under identical conditions.
5. `feat: add guided auto capture` and `feat: add optional camera light` — independently integrate with current capture guides, upload disclosure, retry/cancellation and accessibility; verify unsupported/error cases and actual device behavior when available.

Before any integration, run relevant isolated backend and web tests, type/lint/build checks, and end-to-end API examples against task-owned configuration. Include missing/invalid 14451 bundles, content-derived ID tampering and hashes, capture rejection, correction validation and provenance, authentication/Origin, exact price publication and valuation, and stale or cancelled photo checks. Browser QA requires the repository's shared-resource confirmation and Chrome workflow; physical camera/torch testing requires the appropriate device confirmation. Check bundle hashes before release. A passing synthetic check, frontend build or browser exercise does not establish physical scale, field accuracy, or trading fitness.

The full branch test suite, real ONNX/photo flow, browser accessibility, device torch/camera, consent/deletion behavior, and physical accuracy were not evaluated here.
